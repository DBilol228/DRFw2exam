# Экзаменационное задание по Django REST Framework (DRF)

## Тема: Разработка REST API для социальной сети и мессенджера

**Цель экзамена:** проверить умение проектировать REST API, работать с моделями Django, сериализаторами, Generic Views, ViewSets, JWT-аутентификацией, permissions, фильтрацией и связями между таблицами.

## 1. Общие требования

Разработайте Backend API для социальной сети, в которой пользователи могут:

- Регистрироваться и авторизоваться.
- Создавать и редактировать профиль.
- Загружать аватар.
- Создавать личные чаты и отправлять сообщения.
- Создавать группы и управлять участниками.
- Отправлять сообщения в группы.
- Создавать каналы и подписываться на них.
- Публиковать посты в каналах.

### Технические требования

1. Использовать Django и Django REST Framework.
2. Использовать PostgreSQL или SQLite.
3. Для каждой модели создать сериализатор.
4. Реализовать API с помощью Generic Views, ViewSets или APIView.
5. Настроить JWT-аутентификацию.
6. Настроить permissions для защиты данных.
7. Использовать правильные HTTP-методы и статус-коды.
8. Проверять входящие данные и возвращать ошибки в JSON.
9. Использовать пагинацию для списков сообщений и публикаций.
10. Подготовить документацию API в Swagger или другом формате OpenAPI.

## 3. Account — регистрация и авторизация

Реализуйте следующие API:

### 3.1. Регистрация пользователя

`POST /api/accounts/register/`

Входные данные:

```json
{
  "phone_number": "+992900000001",
  "password": "StrongPass123"
}
```

Требования:
- Проверять уникальность номера телефона.
- Проверять корректность данных.
- Безопасно хешировать пароль.
- Создавать пользователя.
- Возвращать данные созданного пользователя без пароля.

### 3.2. Получение JWT-токена

`POST /api/accounts/token/`

Входные данные:

```json
{
  "phone_number": "+992900000001",
  "password": "StrongPass123"
}
```

Результат: access- и refresh-токены.

### 3.3. Получение текущего пользователя

`GET /api/accounts/me/`

Требования:
- Доступ только для авторизованных пользователей.
- Возвращать данные текущего пользователя.
- Не раскрывать пароль и другие секретные данные.

### 3.4. Изменение пароля

`POST /api/accounts/change-password/`

Требования:
- Проверять старый пароль.
- Проверять новый пароль.
- Сохранять новый пароль безопасным способом.
- Не позволять менять пароль другого пользователя.

## 4. Profile — профиль пользователя

### 4.1. Получение профиля

`GET /api/profiles/{id}/`

Доступно авторизованным пользователям.

### 4.2. Обновление своего профиля

`PATCH /api/profiles/me/`

Входные данные:

```json
{
  "first_name": "Ali",
  "last_name": "Karimov",
  "username": "ali_karimov",
  "bio": "Python Backend Developer"
}
```

Требования:
- Пользователь может менять только свой профиль.
- `username` должен быть уникальным.
- Нельзя менять `user_id` через запрос.
- Необходимо поддерживать частичное обновление.

### 4.3. Поиск профилей

`GET /api/profiles/?search=ali`

Реализовать поиск по имени, фамилии и username.

## 5. Avatar — аватар пользователя

### 5.1. Загрузка аватара

`POST /api/avatars/`

Требования:
- Использовать `multipart/form-data`.
- Принимать файл изображения.
- Проверять тип и размер файла.
- Привязывать аватар к профилю текущего пользователя.

### 5.2. Получение аватара

`GET /api/avatars/{id}/`

### 5.3. Удаление своего аватара

Пользователь не должен иметь возможность удалять аватары других пользователей.

## 6. Chat — личные чаты

### 6.1. Создание личного чата

`POST /api/chats/`

Входные данные:

```json
{
  "user_2": 5
}
```

Требования:
- Первый участник определяется по текущему авторизованному пользователю.
- Нельзя создать чат с самим собой.
- Нельзя передавать `user_1` для подмены отправителя.
- Не создавать повторный чат между теми же двумя пользователями, если он уже существует.

### 6.2. Список личных чатов

`GET /api/chats/`

Возвращать только чаты, участником которых является текущий пользователь.

### 6.3. Получение одного чата

`GET /api/chats/{id}/`

Доступ разрешён только участникам чата.

### 6.4. Удаление чата

`DELETE /api/chats/{id}/`

Реализовать удаление с проверкой прав доступа. Удаление должно быть согласовано с политикой хранения сообщений.

---

## 7. Message — сообщения личного чата

### 7.1. Отправка сообщения

`POST /api/chats/{chat_id}/messages/`

Входные данные:

```json
{
  "content": "Привет! Как дела?"
}
```

Требования:
- Отправитель определяется автоматически.
- Отправлять сообщения могут только участники чата.
- Нельзя передавать `sender` для подмены пользователя.
- Сообщение должно сохранять дату создания.

### 7.2. Список сообщений чата

`GET /api/chats/{chat_id}/messages/`

Требования:
- Проверять участие пользователя в чате.
- Поддерживать пагинацию.
- Сортировать сообщения по дате создания.

### 7.3. Удаление своего сообщения

`DELETE /api/messages/{id}/`

Пользователь может удалять только собственные сообщения, если иное не предусмотрено отдельной политикой администратора.

## 8. Group — группы

### 8.1. Создание группы

`POST /api/groups/`

Входные данные:

```json
{
  "title": "Python Developers"
}
```

Требования:
- Владелец определяется по текущему пользователю.
- Создатель автоматически добавляется в `GroupMember` с ролью `owner`.
- Нельзя передавать другого владельца через запрос.

### 8.2. Список групп

`GET /api/groups/`

Возвращать группы, в которых состоит текущий пользователь.

### 8.3. Изменение группы

`PATCH /api/groups/{id}/`

Изменять название и аватар группы могут владелец и администраторы согласно заданным правилам.

### 8.4. Удаление группы

`DELETE /api/groups/{id}/`

Удалять группу может только владелец.

---

## 9. GroupMember — участники группы

### 9.1. Добавление участника

`POST /api/groups/{group_id}/members/`

Входные данные:

```json
{
  "user": 7
}
```

Требования:
- Добавлять участников может владелец или администратор.
- Нельзя добавлять одного пользователя несколько раз.
- Роль нового участника по умолчанию — `member`.
- Обычный пользователь не может назначать себе роль `owner` или `admin`.

### 9.2. Список участников

`GET /api/groups/{group_id}/members/`

Доступ разрешён участникам соответствующей группы.

### 9.3. Изменение роли

`PATCH /api/groups/{group_id}/members/{member_id}/`

Изменять роли может только владелец группы. Передачу владения следует реализовать отдельно, если она входит в требования.

### 9.4. Выход из группы

`DELETE /api/groups/{group_id}/members/me/`

Пользователь может выйти из группы. Необходимо запретить владельцу оставлять группу без владельца.

## 14. Permissions и безопасность

Необходимо реализовать и продемонстрировать следующие правила:

1. Неавторизованный пользователь не может отправлять сообщения.
2. Пользователь не может читать сообщения чужого личного чата.
3. Пользователь не может изменять чужой профиль.
4. Только владелец может удалять свою группу.
5. Только участники группы могут читать её сообщения.
6. Только владелец канала может создавать, изменять и удалять публикации.
7. Пользователь не может менять свой `user_id`, `sender`, `owner` или другие защищённые поля через запрос.
8. Все проверки доступа должны выполняться на сервере, а не только на стороне клиента.

Продемонстрируйте использование `IsAuthenticated`, `AllowAny`, `has_permission()` и `has_object_permission()` там, где они уместны.
